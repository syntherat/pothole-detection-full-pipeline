## What PAVE is

PAVE is an end-to-end **pothole detection and driver-alert system**, built as an EPICS project at
Vellore Institute of Technology, Bhopal. It detects potholes using **two independent, complementary
sensing modalities**, and surfaces confirmed detections to a driver on a live map.

The design bet: a single modality is not reliable enough.

- A **camera** fails at night, in rain, when the road is occluded by a vehicle ahead, or when the pothole is full of water.
- An **IMU / accelerometer** only knows something *felt* like a pothole — it cannot distinguish a pothole from a speed breaker, a manhole cover, or a bad gear change, and it only sees potholes you already drove into.

Running them as a **cascade** (cheap sensor stage gates the expensive vision stage) gets most of the benefit of both while keeping the compute cost low: YOLO only runs on the small fraction of moments the sensor stage flags.

## The four subsystems

### 1. Sensor / physics pipeline — `pothole_detect_physics/`
Classical physics + classical ML on IMU-style data.

- A **finite state machine** watches vertical acceleration for the signature `DROP → FREEFALL → IMPACT`, and from the freefall duration derives a **depth estimate** and (using speed) a **length estimate**.
- A **RandomForest classifier** trained on a synthetic 200-second, 400 Hz dataset gives a probabilistic pothole score per sample.
- Deliberately trained against a dataset containing **speed breakers labelled as not-pothole**, so the model learns to reject the most common false positive.

Deep dive: [`10-physics-sensor-pipeline.md`](10-physics-sensor-pipeline.md)

### 2. Vision pipeline — `pothole_detection_app/`
YOLO-based object detection with an optional road-segmentation gate.

- **Stage A (optional):** a segmentation model produces a *visible road* mask, excluding vehicles, pedestrians, shadows, vegetation, and roadside objects.
- **Stage B:** a YOLO detector finds potholes on the full frame; detections whose centre falls outside the road mask are **hard-filtered out**, not merely hidden.
- Two Tkinter GUIs, a batch/video CLI, and a full training + evaluation pipeline.

Deep dives: [`11-vision-pipeline.md`](11-vision-pipeline.md), [`12-vision-training-scripts.md`](12-vision-training-scripts.md)

### 3. Map UI — `pothole_map_ui/`
The driver-facing dashboard, and the thing actually named "PAVE" in the UI.

- Dark-themed Google Maps view, live vehicle marker rotated by GPS heading.
- Haversine proximity check; alerts when a known pothole is within **100 m**.
- Live event feed, full-history panel, toast notifications.
- Vanilla HTML/CSS/JS — no framework, no bundler, no npm.

Deep dive: [`13-map-ui.md`](13-map-ui.md)

### 4. Integration layer — `integration/`
The glue that makes the above three one system.

- A shared event dataclass every stage reads and writes.
- Adapters that hide each subsystem's internals behind a simple call.
- Weighted fusion of the sensor score and the vision score into one final decision.
- A file-based bridge to the map UI.

Deep dive: [`14-integration-layer.md`](14-integration-layer.md)

## The cascade in one paragraph

For each row of sensor data: run the physics FSM and the RandomForest. If **both** agree (physics detected a drop-freefall-impact pattern **and** the classifier score is at least 0.5), the event is promoted to Stage 2 — a camera frame and a GPS fix are attached, YOLO runs on that frame, and a weighted blend of the two scores (40 % sensor, 60 % vision) decides whether the event is confirmed. Confirmed events are appended to a JSON file, which the map UI polls every 3 seconds and turns into a red marker plus a proximity alert.

Full detail with the exact numbers: [`03-architecture-dataflow.md`](03-architecture-dataflow.md).

## Maturity — what is real and what is staged

Be precise about this; Rule 6 depends on it.

| Piece | Status |
|---|---|
| Physics FSM | Real, working algorithm |
| RandomForest classifier | Real, trained — but on **synthetic** data only |
| Sensor dataset | **Synthetic**, generated by `generate_dataset.py`. No real vehicle logs exist in this repo. |
| YOLO pothole detector (`best.pt`) | Real trained weights, committed (~40 MB) |
| Road segmentation model (`road_seg.pt`) | Real trained weights, committed (~20.5 MB). `yolo11s-seg`, 7 classes, trained on public driving datasets. **The segmentation branch runs but has never produced a non-empty mask** — 0/16 dashcam and 0/45 CARLA frames predict `visible_road`, so every detection comes from the lower-60 % crop fallback. See issue #30; do not describe the system as two-stage |
| Frame-to-sensor-row association | **Mocked on the default path** — `frame_provider.get_mock_frame()` picks a deterministic stand-in image, unrelated to the sensor event. **Real on the CARLA path** since 2026-09-08: `carla_frame_provider.py` keys frames by timestamp on the simulator's own timebase, which closed issue #18 |
| GPS | **Mocked** in the integration path (`simulate_gps`) and in the filtered GUI (`_random_dummy_gps`). Real only in the browser UI, via the Geolocation API. |
| Integration to map transport | Prototype — a JSON file polled over HTTP, not an API |
| Fusion weights | Hand-chosen, not fitted |

The single largest missing piece is **time-synchronised sensor and camera data from a real vehicle**. Everything downstream of `frame_provider.py` is waiting on it.

## Glossary

| Term | Meaning here |
|---|---|
| **Stage 1 / sensor stage** | Physics FSM + RandomForest, run per CSV row. Cheap. |
| **Stage 2 / vision stage** | YOLO on a frame. Expensive; only runs on Stage-1 hits. |
| **Cascade** | The pattern of gating Stage 2 behind Stage 1. |
| **Fusion** | The weighted combination of `ai_score` and `vision_score` into `final_confidence`. |
| **Candidate event** | A `PotholeCandidateEvent` — one row's worth of pipeline state, whether or not it was confirmed. |
| **Confirmed event** | A candidate whose `final_decision` is `True`. Only these reach the map. |
| **Two-stage detection** | Vision-internal term: road segmentation, then pothole detection. Unrelated to Stage 1 / Stage 2 above. **These two "stage" vocabularies collide — be explicit about which you mean.** |
| **Visible road** | Road surface actually visible to the camera, i.e. road minus occluders (vehicles, pedestrians, shadows). |
| **Flagged frame** | In the filtered GUI: a video frame with at least one accepted detection, saved to disk with metadata. |
| **EPICS** | The academic programme the sensor subsystem was originally built for. Also the historical folder name for `pothole_detect_physics/` — the root README still uses the old name in places. |
